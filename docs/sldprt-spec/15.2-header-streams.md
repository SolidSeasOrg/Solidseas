# 15.2 The binary header streams

This section gives ten members: the model header (`Header2` and its copy
`Contents/Config-0-ModelHeader`), the configuration manager
(`Contents/CMgr`, `Contents/CMgrHdr2`), the custom-property store
(`Contents/CusProps`), the light-weight data (`Contents/Config-0-LWDATA`), the
display state (`ThirdPtyStore/VisualStates`), the motion studies
(`ThirdPty/Animator`), the save history (`_MO_VERSION_17000/Biography`) and
the document definition (`Contents/Definition`). Each is written uncompressed
and none is wrapped in ZLB. All but `Animator`, `VisualStates` and `LWDATA`
are one MFC `CArchive` from the first byte; those three start with a few
plain fields and then open their archive, where the listing says
`@archive start 1`. Every archive in this section is its own and starts at 1.

| Member | Listing | Bytes in o01, o02, o12 | o02: typed, hex, slot bytes |
|---|---|---|---|
| `Header2` | `header2.srl` (includes `model-header.srl`) | 2,091, 2,327, 2,483 | 2,002, 3, 322 |
| `Contents/Config-0-ModelHeader` | `config-0-modelheader.srl` (the same) | 2,091, 2,327, 2,483 | 2,002, 3, 322 |
| `Contents/CMgrHdr2` | `cmgrhdr2.srl` | 137, 137, 137 | 125, 0, 12 |
| `Contents/CusProps` | `cusprops.srl` | 101, 137, 137 | 137, 0, 0 |
| `Contents/Config-0-LWDATA` | `config-0-lwdata.srl` | 1,437 in each | 1,009, 0, 428 |
| `ThirdPtyStore/VisualStates` | `visualstates.srl` (includes `visual-properties.srl`) | 1,482, 1,593, 1,704 | 1,549, 0, 44 |
| `Contents/CMgr` | `cmgr.srl` (includes `visual-properties.srl`) | 1,762, 1,981, 2,043 | 1,702, 27, 252 |
| `ThirdPty/Animator` | `animator.srl` | 342 in each | 262, 0, 80 |
| `_MO_VERSION_17000/Biography` | `biography.srl` | 1,637, 1,635, 1,645 | 275, 0, 1,360 |
| `Contents/Definition` | `definition.srl` | 3,809 in each | 3,577, 14, 218 |

Every listing gives its member byte for byte in o01, o02, o03, o07 and o12.
VERIFIED (`tests/test_sldprt_spec.py`, each case assembled with the part's
one slot dict). Typed bytes include runs of zero
bytes written as `rep N 00` where the fields there are not decoded; the
section says so wherever that is the case. The slot bytes of the Biography
are almost all folder paths, which the generator does not write (15.2.10).

## 15.2.1 How this section is proved, and what the generator may leave stale

The design slots of each case are written down from what the part is: its
features after the fixed ones (`Sketch1` and `Boss-Extrude1`, and in o12
`Sketch2` and `Boss-Extrude2`), their node ids, and each body's box. The
identity and free slots (times, the saving account, folder paths, session
counters, the view at save) are read from the fixture when the case runs, by
walking the listing over the member and taking each such field where the
listing reaches it. Every constant, every length and every design value is
still compared with SOLIDWORKS' bytes.

What SOLIDWORKS accepts: the candidates b3 and b4 of
`docs/NATIVE_SLDPRT_WRITER.md` 6.1 are the empty part o01 with only
`Contents/Config-0` and the feature stream taken from o02 (b4 also moved the
box to 40 x 30 x 10 mm). All ten members of this section were o01's: no
feature in the log, no body in the configuration manager, no sketch in the
display state, an empty box, o01's times and counters. Both opened with no
warning, rebuilt to their features (6,000 and 12,000 mm³) and took a
dimension edit. VERIFIED (SOLIDWORKS 2024 SP1, 2026-10-19). So every field
below that describes the features or the body is a cache SOLIDWORKS
tolerates in its empty-part form. The generator nevertheless writes the
form SOLIDWORKS itself writes for the design, which the listings give and
which the fixtures prove byte for byte, so that the file agrees with
itself; that SOLIDWORKS accepts that form from the generator is a
HYPOTHESIS until a generated part is checked on the PC, and the empty-part
form is the fallback that is VERIFIED.

## 15.2.2 The model header: `Header2` and `Contents/Config-0-ModelHeader`

`Header2` and `Contents/Config-0-ModelHeader` are the same bytes. VERIFIED
(14 of 14 fixture parts; in o13, which has two configurations,
`Config-1-ModelHeader` differs and is out of scope). Both listings include
`model-header.srl`. The stream is one `CArchive`.

### 15.2.2.1 The head and the accounts

A `moHeader_c` object (schema 1) with a u32 1, then an `su_CStringArray`
(schema 0) of the accounts that saved the document: a u16 count and one
`CString` each. Every fixture has one entry, the account that made it
(`docs/FORMAT.md` 12.2 has the corpus reading: usually the last saver is
last). The listing writes one entry holding `doc.author`, the same account
as core.xml's last saver in every fixture (VERIFIED, 5 parts); the generator
writes `SolidSeas` (README 15.0.6). That SOLIDWORKS accepts any text there is
a HYPOTHESIS. A
second `su_CStringArray` follows with one empty string; its meaning is not
decoded (constant in every fixture).

### 15.2.2.2 The log

An `suObList` (schema 1) with a u16 count, then one `moLogs_c` (schema 1)
per node of the feature tree:

| Field | Type | Meaning |
|---|---|---|
| count | u16 | the number of stamps, 1 or 2 |
| stamps | `moStamp_c` objects | each: u16 kind (0 created, 1 modified), u32 0, u32 Unix time, `CString` `"Created"` or `"Modified"` |
| id | u32 | the node's id |
| name | `CString` | the node's name |

The first 17 nodes (ids 0 to 16, `Part1^Assem1` to `Equations`) come from
the part template and carry the template's own time, `tpl.unix`; the planes,
the origin and the material node also carry a modified stamp at that time.
The next seven (ids 17, 18 and 21 to 25, `Notes` to `Selection Sets`; ids 19
and 20 are not used) are made with the document and carry its creation
time, `doc.created`. The listing gives all 24 by name. VERIFIED (5 parts).
`Folder ` has a trailing space in every fixture.

Then one node per feature of `$features`, in timeline order: the u16 count is
2 for a sketch, logged created and modified, and 1 for an extrusion, logged
created; the times are the feature's `created` and `modified` fields and the
id is its `id`. The u16 count of the list is `=24+len($features)`. VERIFIED
(o02, o03, o07: `Sketch1` and `Boss-Extrude1`; o12: also `Sketch2` and
`Boss-Extrude2`). In o11, outside scope, a sketch that a cut consumed is
logged created only, so whether a sketch has a modified stamp depends on how
it was used: within the scope of boss extrusions every sketch has one.
VERIFIED (o02, o07, o12) and UNKNOWN beyond.

### 15.2.2.3 Node ids

The node ids are the ones section 15.5 gives the features. In the fixtures
`Sketch1` is 26, `Boss-Extrude1` 32, `Sketch2` 33 and `Boss-Extrude2` 40. After
the list come the u32 `tpl.unix2` (a second template time), the u32
`hdr.next_id`, a u16 0 and the u32 `doc.stamp`. `hdr.next_id` is the last
feature's id plus one, and 26 with no features (one more than `Selection
Sets`). VERIFIED (26 in o01, 33 in o02, o03 and o07, 41 in o12; also 45 in
o11, whose last feature is 44).

### 15.2.2.4 Stamps and times

| Slot | What it is | Evidence |
|---|---|---|
| `doc.created` | the document's creation time, the same as element 0 of `ModelStamps` (15.1) | VERIFIED (5 parts) |
| `doc.unix` | the save time; with features it is also when the configuration last changed and was last rebuilt | VERIFIED (4 parts with features; equal to `core.xml` `modified`) |
| `tpl.unix`, `tpl.unix2` | two times from the part template, one second apart, the same in every fixture | VERIFIED (5 parts) |
| `doc.stamp` | a document-wide change stamp, the same as element 1 of `ModelStamps` and in `CMgrHdr2`, `CMgr`, `LWDATA`, `SwDocContentMgrInfo` and `DLUpdateStamp` | VERIFIED (5 parts: 102 in o01, 120 in o02, o03 and o07, 140 in o12) |
| `doc.stamp2` | a second stamp, the same as element 2 of `ModelStamps` | VERIFIED (101 in o01, 105 in o02, o03 and o07, 111 in o12) |

In the empty part the two "changed" and "rebuilt" fields hold the template's
times (`tpl.unix2` and `tpl.unix`); with features they hold `doc.unix`. The
listing writes that choice with `@if =len($features)>0`.

Both stamps grow as features are added (o11, o13 and o14 hold 130 and
117, 150 and 111, 136 and 107). `doc.stamp` is one more than the last
feature id of the feature stream (15.5.4); how `doc.stamp2` relates to the
features beyond the mass tags of 15.4.11 is UNKNOWN. Both are free: the
generator writes the values of the one rule in 15.6.6. b3 and b4 carried
o01's 102 and 101 beside o02's features and were accepted (15.2.1).
VERIFIED.

### 15.2.2.5 The document object

A `moExtObject_c` (schema 1), then two `moCStringHandle_c` objects (schema 1),
the first with an empty string and the second with `doc.name`, the internal
document name (section 15.6); then three bytes `02 00 00` (not decoded),
`doc.created`, three empty strings, a u16 0, the change time (15.2.2.4), u32
1 and 0, i32 -1, the configuration's name `"Default"`, 16 zero bytes,
`doc.stamp2`, two u32 0, `doc.created` again, 18 zero bytes, u32 2, the
rebuild time, and an empty `suObList` (u16 0) followed by two u32 0.
VERIFIED (5 parts). `doc.name` is SOLIDWORKS' session name for a new document
(`PartN`), a free slot; the generator writes `Part1` (15.6.6).

### 15.2.2.6 The bounding sphere and box

Then a u32 1 and ten doubles in metres: the centre of a bounding sphere, the
box's far corner `model.max`, its near corner `model.min`, and the sphere's
radius. The empty part writes u32 0 and no doubles. VERIFIED (5 parts). That
the second triple is the far corner and the third the near one is VERIFIED
by `LWDATA`'s empty form (15.2.5), where the far corner is (-1, -1, -1) and
the near one (1, 1, 1); every fixture's near corner is the origin.

The sphere: each body's box gives the sphere through its corners, centre
`(min+max)/2` and radius half the diagonal; with several bodies the spheres
are merged in body order, each time into the smallest sphere holding both,
radius `R = (d + r1 + r2)/2` for centres `d` apart. The merged centre lies on
the line between the two centres; `Header2` computes it from the newer
sphere, `c = c2 - (c2 - c1)/d * (R - r2)` (the slot `hdr.centre`), and
`LWDATA` and `Contents/Config-0` from the older one,
`c = c1 + (c2 - c1) * (R - r1)/d` (the centre of `model.sphere`), which differ
in the last bits. All three write the radius `model.sphere.3`. VERIFIED bit
for bit on o12 (two bodies) and on the single bodies of o02, o03 and o07;
the merge rule for three or more bodies is a HYPOTHESIS. Section 15.6.3 gives
the exact order of operations.

These are caches (`docs/NATIVE_SLDPRT_WRITER.md` section 5). The generator
computes them from the design by section 15.6.3, one box per body. A sphere that does not match the bodies is accepted: b1, o12's two
bodies with o02's one-box caches, rebuilt to 8,000 mm³. VERIFIED. After the
box: three i32 -1, u32 1, 40 zero bytes, u32 1, 16 zero bytes, u32 1 (not
decoded, constant).

## 15.2.3 `Contents/CMgrHdr2`

### 15.2.3.1 The header

The configuration manager's header, one `CArchive`: a `dmConfigMgrHeader_c`
(schema 1) with a u16 count of configurations (1), then a
`dmConfigHeader_c` (schema 1): u32 1, the name `"Default"`, u32 0,
`doc.stamp`, the name again, i32 -1, u32 0, two empty strings, the flags
u32 0x80400180 (not decoded), u32 0, the configuration's change count, u32
101, the change time (15.2.2.4) and u32 2. VERIFIED (5 parts).

### 15.2.3.2 The change count

The change count is `=101+len($features)`: 101 in o01, 103 in o02, o03 and
o07, 105 in o12. VERIFIED on those 5 parts. It counts more than features:
o11 (6 features) has 106, o13 (two configurations) 107 and o14 (o02 with
property edits) 104, so it is a change counter that the in-scope parts
happen to step once per feature. The same value is in `Contents/Config-0`
(section 15.4 should use the same expression). HYPOTHESIS that SOLIDWORKS
needs it to agree with anything.

## 15.2.4 `Contents/CusProps`

The custom-property store with no properties, one `CArchive`: a
`moCusPropMgr_c` (schema 1) with i32 -1, u32 1 and the number of
configurations (1); then per configuration its id (u32 0), a
`moCusPropContainer_c` (schema 1), a `moFilePropContainer_c` (schema 1)
holding a null object (u16 0, where o04 to o06 hold an `suObList` of
properties, `docs/FORMAT.md` 11.1) and a u16 0, then, once the part has a
body, a `moCutListPropContainer_c` (schema 1) and 8 zero bytes, or in the
empty part a null object (u16 0); then 6 zero bytes. VERIFIED (5 parts;
the cut-list container appears in every fixture part with a body and in
none without). The first i32 is -1 with no properties; it is 2 in o04 and
o05 (three properties), 3 in o06, 4 in o09 and o10 and 7 in o14, so it is
most likely the index of the last property. HYPOTHESIS. The stream has no
slot other than `$features`.

## 15.2.5 `Contents/Config-0-LWDATA`

### 15.2.5.1 The head

`doc.stamp`, then the ten doubles of 15.2.2.6 with no flag: the sphere's
centre as `LWDATA` computes it (`model.sphere`, centre), `model.max`,
`model.min` and the radius (`model.sphere`, radius). The empty part writes the centre at the origin, the far corner
(-1, -1, -1), the near corner (1, 1, 1) and the radius -2. Then f64 1000.0
(not decoded). VERIFIED (5 parts).

### 15.2.5.2 The crosshatch

A `CArchive` starts here. A `gcXhatch_c` (schema 1) with the pattern
`"ANSI31 (Iron BrickStone)"`, f64 0.0, 1.0 and 0.0 (angle and scale,
HYPOTHESIS), u32 1, two i32 -1, u32 0, then a u16 3: the number of plane
records. VERIFIED (5 parts; o05 and o14, with a material, are 14 bytes
shorter, out of scope).

### 15.2.5.3 The plane records

One `moLWPlaneNodeData_c` (schema 1) per reference plane, Front, Top and
Right: the plane feature's class `"moRefPlane_c"`, its name, its node id
(2, 3, 4), u32 0 and 1, its origin and normal, the display rectangle (centre,
far corner, near corner in model space, and half its diagonal), its axes as
three rows of doubles, a u32 that is 1 for Front and 0 for the others, u32
32764, f64 0, 0, 0, 1.0, 0, i32 -4, half the rectangle's width and height
each written positive then negative, and the display data's class name
`"moDefaultRefPlnData_c"`. VERIFIED (5 parts).

The rectangle is a cache sized to the model: on the plane's two axes the
model box grown by 5% of its extent on each side, flat on the normal; half
sizes 0.55 times the box's extents (the Right plane's first axis is the
model's z). It is the rectangle the feature stream draws (15.5.5), and the
listing writes the shared slots `planes.front`, `planes.top` and
`planes.right`: `centre`, `max`, `min`, `radius`, and the half sizes `hu`
and `hv`. Section 15.6.3 gives their exact rule. VERIFIED bit for bit on all
five parts. With no body the rectangle is the template's default: centre at
the origin, corners at ±88.99 mm and ±55 mm on the plane's axes, half sizes
0.08899 and 0.05500000000000001 m. Stale plane sizes are accepted: a1 and b3
rebuilt with them. VERIFIED.

### 15.2.5.4 The tail

Six zero bytes, a u32 that is 1 once the part has features (0 in o01 and
in o09, which has an imported body and no sketch), a u32 `lw.flag`, and 8
zero bytes. `lw.flag` is 0 in o01 to o07 and 1 in o09 to o17, o17 included,
which is o02's box under another name made later in the same session; so it
records session state, not the design. Free; the generator writes 0, which
b3 carried and SOLIDWORKS accepted. VERIFIED (counts); its meaning is
UNKNOWN.

## 15.2.6 `ThirdPtyStore/VisualStates`

The display state: which nodes are shown, and with what appearance.

### 15.2.6.1 The head

u32 17000 (the saving version, `docs/FORMAT.md` 7.5) and u32 0, then a
`CArchive`: a `visStateKeyData_c` (schema 1) with eight u32 (5, 0, 1, 0, 1,
1, 1, 1, not decoded), the display state's name `"<Default>_Display State
1"`, 16 zero bytes and the number of components that follow,
`=5+len($sketches)`. VERIFIED (5 parts).

### 15.2.6.2 The part

A `moCompHolder_c` (schema 1) with its unit data (a `moUnitComponent_c`,
schema 1: 43 zero bytes, four i32 -1, 20 zero bytes), u32 17000, u32 1, 1,
2, a `visStateVisualPropertiesAttribute_c` (schema 1) holding u32 1 and the
part's appearance (15.2.9, with the texture
`"<SystemTexture>\graphics\materials\color.p2m"`), and a
`visStateVisualStateAttribute_c` (schema 1), labelled `shown`, holding u32 1,
1, 6, 1, 0. VERIFIED (5 parts).

### 15.2.6.3 The nodes

One record per node: the sketches newest first (`@for f in $sketches
reversed`), then the Origin (id 5) and the
Right, Top and Front planes (ids 4, 3, 2). A record is a `moCompFeature_c`
(schema 1) with its unit data, u32 17000, the node id, the node's creation
time (`$f.created` for a sketch, `tpl.unix` for the template's nodes), u32
1, 1, 2, then two references:

- the appearance attribute: the first record writes a new
  `visStateVisualPropertiesAttribute_c` labelled `plain` (u32 1 and a null
  object), every later record refers to it;
- the visibility attribute: sketches and the Origin refer to `shown`; the
  Right Plane writes a new `visStateVisualStateAttribute_c` labelled
  `hidden` (u32 1, 0, 6, 1, 0) and Top and Front refer to it.

The stream ends with a null object (u16 0) and 6 zero bytes. VERIFIED (5
parts: o01 has no sketch record and its Origin record writes `plain`; o12
has `Sketch2` then `Sketch1`). Extrusions have no record.

## 15.2.7 `Contents/CMgr`

The configuration manager, one `CArchive`.

### 15.2.7.1 The manager

A `moConfigurationMgr_c` (schema 1): u16 0, 8 bytes `00 00 00 00 00 00 00
40` (not decoded), i32 -1, u32 0, an empty string, 14 zero bytes, then the
configuration data of 15.2.7.2.

### 15.2.7.2 The configuration data

Written twice, by the manager and by its configuration: u32 101, 13 zero
bytes, u32 17000, 8 zero bytes, u32 2024016 (the saving build,
`docs/FORMAT.md` 7.3), u16 0, an empty string, u8 0, u16 0xFFFF and 0, u8
3, two i32 -1, f32 -1.0, 14 zero bytes, u32 1, 6 zero bytes, i32 -1, then
`cmgr.created`, the time the configuration was made, as a FILETIME stored
high word first (two u32), then u16 2, u32 0x0005579C and u32 1 (not
decoded). VERIFIED (5 parts). `cmgr.created` is within a second after
`doc.created` in every fixture; the generator writes `doc.filetime`.

### 15.2.7.3 The configuration

A `moPartConfiguration_c` (schema 1) named by a `moNodeName_c` (schema 1)
`"Default"`, then 16 bytes not decoded, an empty string, u32 0, the part's
appearance (15.2.9) with the texture path `cmgr.texture`, 8 zero bytes and
the configuration data again. Then an empty string, i32 -1, u32 0x80400180,
an empty string, the newest node's id `=$hdr.next_id-1`, `doc.stamp`, 100
zero bytes, u32 1, 40 zero bytes, two empty strings, 28 zero bytes, an
identity rotation (nine doubles), u32 1, u16 0, u32 0x259EE3D0 and u32 0.
VERIFIED (5 parts).

`cmgr.texture` is the appearance file as an absolute path into the
SOLIDWORKS installation. The generator writes
`"<SystemTexture>\graphics\materials\color.p2m"`, the form SOLIDWORKS itself
writes for the same file in `VisualStates` (15.2.6.2). That `CMgr` accepts it
is a HYPOTHESIS.

### 15.2.7.4 The bodies

The listing reads `bodies` (15.6.4): one item per solid body in timeline
order, `id` 101 for the first body and one more for each after it, and
`feature` the node id of the boss extrusion that made it. Within scope each
boss extrusion makes one body (o12's second extrusion has merge off). The
listing writes the body count four times and three lists over them (ids with
u32 0; id, a `moLinkedAtomIdNode_c` with the id, u16 1, the feature's id and
18 zero bytes; ids newest first, `@for b in $bodies reversed`), each inside
fields not decoded. VERIFIED (o01 none, o02, o03 and o07 one, o12 two).
Which feature makes which body when merge is on, and the id of a body made by
something other than a boss extrusion, are UNKNOWN.

### 15.2.7.5 The document object and the build times

Once the part has features: u32 1, then the document object of 15.2.2.5 up to
its three empty strings, 18 zero bytes, `"Default"` and 16 zero bytes. The
empty part writes u32 0 instead. Then 4 zero bytes, an empty string, 4 zero
bytes, an empty `suObList`, and the bodies newest first with, for each, the
id of the feature that made it (`feature`) and its `time`, a FILETIME high
word first within a second of the save. Then 8 zero bytes, u32 1, 8 zero bytes, a
second empty `suObList`, 26 zero bytes, u32 2, 4 zero bytes, an empty
string, 12 zero bytes, i32 -1 and 4 zero bytes. VERIFIED (5 parts). The
generator writes `doc.filetime` for every body's `time`.

## 15.2.8 `ThirdPty/Animator`

The motion studies: u32 17000, then a `CArchive`: a `moAnimationManager_c`
(schema 1) with i32 -1 and the number of studies (1), and the template's
empty study, a `moAnimKeyData_c` (schema 1) named `"Motion Study 1"` with its
id `anim.guid`, an empty string and fields not decoded, ending with u16 1 and
the name of the study shown. VERIFIED (5 parts). o13, outside scope, has no
study and a 44-byte stream.

`anim.guid` is a GUID in braces in upper-case hexadecimal. Each new document
gets a new one and Save As keeps it: o02 to o06 share one, o01 and o07 each
have their own. VERIFIED (7 parts). It is identity: the generator writes a
new random GUID (version 4) for each part.

## 15.2.9 The part's appearance: `moVisualProperties_c`

`visual-properties.srl` defines it once for `CMgr` and `VisualStates`: the
colour as a COLORREF, 0x00EED1CA (red 202, green 209, blue 238), the
appearance `"Steel"`, its base `"defaultplastic"`, the colour again, floats
and flags not decoded, the appearance file (the `TEXTURE` parameter), and
empty strings and zero runs. The two uses differ only in the texture path
and in one u32, 3 in `CMgr` and 33 in `VisualStates` (the `N` parameter, not
decoded). VERIFIED (5 parts each). With a material (o05, o14) both streams
change; out of scope.

## 15.2.10 `_MO_VERSION_17000/Biography`

### 15.2.10.1 The records

The save history, one `CArchive`: a `moBiography_c` (schema 1) with the
number of records, 2 in every fixture part: the document's creation from
the template, and the session that saved it. VERIFIED (5 parts; the same
shape in o13).

### 15.2.10.2 A record

A record's head is u32 17000, u32 2024016, u32 1, 9, 12 (not decoded), the
Windows version (platform, major, minor and build, four u32), an empty
service-pack string and a u16 locale id. Then two groups. A group is a
FILETIME (u64), a u32 not decoded, and six folder entries; an entry is a
`CString` path, u32 3 and a u64 not decoded that is the same in every entry
of the group. An empty group is all zero: no time, u32 0, and six entries
with an empty path, u32 0 and u64 0. VERIFIED (5 parts; `docs/FORMAT.md`
section 13 has the corpus reading).

### 15.2.10.3 What the two records hold

| Record | First group | Second group |
|---|---|---|
| 1, creation | empty | the template's time (`bio.made.time`) and its two values not decoded (`bio.made.tag`, `bio.made.x`), then the system folder, the Windows folder, the working folder, the temporary folder twice and the template's path (`bio.made.system`, `.windows`, `.work`, `.temp`, `.template`) |
| 2, the save | when the session began work on the document (`bio.open.time`, `.tag`, `.x`), then the same six folders (`bio.open.system` and so on) | the save time (`bio.save.time`, `.tag`, `.x`), then `"*"`, `"*"`, the folder saved to (`bio.save.folder`), `"*"`, `"*"` and the file saved (`bio.save.file`) |

`"*"` stands for "unchanged". VERIFIED (5 parts). The opening time is within
a second after `doc.created` and the save time within a second after
`doc.unix`.

Everything in a record but the release fields describes a person's machine:
their folders, the file's path, the Windows build and the locale. The
generator writes every path as an empty string, keeping u32 3 and writing
u64 0 after it, every u32 not decoded as 0, the FILETIMEs as `doc.filetime`,
the Windows version as platform 2, version 10.0, build 0, and the locale
1033 (English, United States, the language of the template's names). That
SOLIDWORKS accepts these neutral values is a HYPOTHESIS; it is history that
nothing the fixtures show reads back.

## 15.2.11 `Contents/Definition`

### 15.2.11.1 The document type

u32 7, 0, 50, 1, 1 (not decoded), then the document-type GUID
`{83A33D30-27C5-11CE-BFD4-00400513BB57}` (a part) in little-endian GUID byte
order (`docs/FORMAT.md` 6), three zero bytes and u8 1. VERIFIED (5 parts).

### 15.2.11.2 The view at save

A rotation (nine doubles by rows), a zero translation, a scale of 1.0, u16 0,
the window's centre in model space and its zoom (four doubles), u8 0 and u16
3 and 1; here followed by nine bytes not decoded. The same view is written
again inside the user model environment (15.2.11.4). These are window state
and free: o02, o03 and o12 hold the isometric view, o07 the same rotation
with another centre and zoom, o01 the template's. The generator writes the
isometric rotation, rows (1/√2, -1/√6, 1/√3), (0, 2/√6, 1/√3) and
(-1/√2, -1/√6, 1/√3), computed in double precision, the centre at the origin
and a zoom of 1.0. A view that does not fit the model is accepted: b3 and b4
carried o01's view. VERIFIED. That SOLIDWORKS accepts the generator's view
is a HYPOTHESIS.

### 15.2.11.3 Line styles and line fonts

A `CArchive` starts here. A `moISO_c` (schema 1) with seven `moLineStyle_c`
(schema 1): name, description, a u16 count of dash elements, the elements as
doubles (dash positive, gap negative) and a u8 flag; then a
`uiLineFontMgr_c` (schema 1) with a u16 count (40) of entries, each a kind of
entity and a `uiLFConfig_c` (schema 1): the line style's name, a u16 not
decoded, the weight f32 -1.0 (the default) and a u16. All constant, from the
template. VERIFIED (5 parts).

### 15.2.11.4 The user model environment

u16 1, then a `uiUserModelEnv_c` (schema 1): the account that saved
(`doc.author`, the same account as in `Header2` in every fixture), u16 1, 1,
1230, 10, 3392, 10 (not decoded), u32 0, u8 1, the view of 15.2.11.2 again,
f64 -1.0, an empty string, and fields not decoded, constant in every fixture.
That SOLIDWORKS accepts `SolidSeas` here is a HYPOTHESIS.

### 15.2.11.5 The bill of materials and the design journal

A `moBomInfoMgr_c` (schema 1) and a `uoJournal_c` (schema 0) naming
`"Design Journal.doc"`, then fields not decoded ending with f64 1000.0.
Constant. VERIFIED (5 parts).

## 15.2.13 What is not known

- Whether SOLIDWORKS reads any of these streams back on open rather than
  rebuilding them: b3 and b4 show it accepts the empty part's form with
  features, which suggests it does not, for these ten. Whether it accepts
  the neutral account, path and machine values of 15.2.2.1, 15.2.7.3,
  15.2.10 and 15.2.11.4 is a HYPOTHESIS to settle with the first generated
  part on the PC.
- The meaning of `doc.stamp2`, of `lw.flag`, of the fields marked "not
  decoded", and of the change count of 15.2.3.2 beyond the in-scope parts.
- The bounding-sphere merge for three or more bodies, and the body list when
  extrusions merge (15.2.7.4).
- Configurations, custom properties, materials and imported bodies change
  `CusProps`, `CMgr`, `CMgrHdr2`, `LWDATA` and `VisualStates` (o04 to o06,
  o09, o13, o14): out of scope for the generator and not specified here.

# 15.3 The 3DEXPERIENCE exchange members

Two members, `Contents/3DExperienceExchange2` and
`Contents/3DExperienceExchange_ConfigHeader`, are each a complete UnQLite
database file of three 4096-byte pages (12,288 bytes). UnQLite is an
open-source embedded key/value store (BSD licence); the layout below is the
one its public source writes (`pager.c` for the database header,
`lhash_kv.c` for its linear-hash storage engine). Each record's value is a
MessagePack document.

| Member | Listing | Proved on |
|---|---|---|
| `Contents/3DExperienceExchange2` | `listings/3dexperience-exchange2.srl` | o01, o02, o03, o07, o12 |
| `Contents/3DExperienceExchange_ConfigHeader` | `listings/3dexperience-configheader.srl` | o01, o02, o03, o07, o12 |

## 15.3.1 What the two databases hold

`3DExperienceExchange2` holds five records: one for each of the three
standard reference planes, a table of contents (key `TOC`) and a document
record. `3DExperienceExchange_ConfigHeader` holds one record, the header of
the configuration `Default`.

Neither member depends on the design. VERIFIED (o01, o02, o03, o07, o12):
once the GUIDs and the creation time are set aside, the five parts give the
same records, value for value, although o01 has no features, o02, o03 and
o07 have a sketch and an extrusion of two different depths, and o12 has two
extrusions. There is no record for a sketch or a feature. The members carry
no name, path, account or licence.

Every byte of both members is accounted for by the listings. The database
file carries no checksum (UnQLite keeps checksums only in its rollback
journal, which is not stored); the only computed values are the key hashes
(15.3.3).

### Slots

| Slot | Kind | Type | Meaning, and what the generator writes |
|---|---|---|---|
| `exch.time` | derived | fields `year`, `month` (1 to 12), `day`, `hour`, `minute`, `second` | the database creation time: the calendar fields of `doc.unix` in UTC (15.3.2). Both members carry the same time |
| `exch.front`, `exch.top`, `exch.right` | identity | text, 36 characters | the GUIDs keying the Front, Top and Right Plane records. The generator writes `Identity.exch_front`, `exch_top`, `exch_right` (15.6.6): new random version 4 GUIDs, as lowercase hexadecimal in the 8-4-4-4-12 form with hyphens |
| `exch.doc` | identity | text, 36 characters | the GUID keying the document record; `Identity.exch_doc`, a new random version 4 GUID, same form |
| `exch.config` | identity | text, 36 characters | the GUID keying the configuration header record; `Identity.exch_config`, a new random version 4 GUID, same form |
| `exch.hash.front`, `.top`, `.right`, `.doc`, `.config` | derived | u32 | the key hash (15.3.3) of the ASCII bytes of `exch.front` and so on |
| `exch.toc` | free | list of three texts | the plane GUIDs in the order the table of contents lists them (15.3.6). The generator writes `[$exch.front, $exch.top, $exch.right]` |

VERIFIED (o01, o02, o03, o07, o12): each GUID is a version 4 GUID (third
group starting `4`, fourth group starting `8` to `b`), and none of the five
appears in any other member of its part, as text in either case, as UTF-16,
or as 16 bytes in either byte order. Nothing else in the part has to agree
with them, so fresh random GUIDs are consistent with the rest of a generated
part.

VERIFIED (o02 and o03, the same part saved twice): the second save keeps
`3DExperienceExchange2` byte for byte, GUIDs and time included, while
`3DExperienceExchange_ConfigHeader` gets a new GUID for its record and keeps
the creation time. The plane and document GUIDs therefore belong to the
document and the configuration header's GUID to the save; a generator,
writing each part once, makes all five new.

## 15.3.2 Page 0: the database header

| Offset | Size | Field | Value |
|---|---|---|---|
| 0 | 7 | signature | `unqlite`, ASCII |
| 7 | 4 | magic number | `0xDB7C2712`, big-endian |
| 11 | 2 | creation date | MS-DOS date, big-endian u16 (below) |
| 13 | 2 | creation time | MS-DOS time, big-endian u16 (below) |
| 15 | 4 | sector size | 512, big-endian |
| 19 | 4 | page size | 4096, big-endian |
| 23 | 2 | length of the storage engine's name | 4, big-endian |
| 25 | 4 | storage engine | `hash`, ASCII |
| 29 | 4067 | | zero |

All UnQLite integers are big-endian.

The creation time is packed as UnQLite packs it, which is not quite the
MS-DOS convention: the month is counted from 0.

- date = (year minus 1980) times 512, plus (month minus 1) times 32, plus day
- time = hour times 2048, plus minute times 32, plus second divided by 2 (rounded down)

The four bytes read as one big-endian u32 are date times 65,536 plus time.
VERIFIED (o01, o02, o03, o07, o12): read with the month counted from 0, the
field gives each part's save date, and its time is the creation or the
modification time of `docProps/core.xml` rounded down to an even second;
read with the month counted from 1, every part would be dated a month early.
The fields are UTC, like `core.xml`, and are those of the save instant
`doc.unix` (core.xml `modified`): the packed seconds field keeps only even
seconds, and with that, `doc.unix` gives the stored date and time in both
members of all five parts (VERIFIED). So `exch.time` is derived from
`doc.unix` (15.6.5).

## 15.3.3 Page 1: the hash engine's header and the key hash

| Offset | Size | Field | Value |
|---|---|---|---|
| 0 | 4 | engine magic number | `0xFA782DCB` |
| 4 | 4 | hash of `chm@symisc` | `0x03F523F5`: the key hash of these ten ASCII bytes, by which UnQLite checks it is using the same hash function |
| 8 | 8 | first page of the free-page list | 0, none |
| 16 | 8 | split bucket | 0 |
| 24 | 8 | maximum split bucket | 1 |
| 32 | 8 | next page of the bucket map | 0, none |
| 40 | 4 | entries in this page of the map | 1 |
| 44 | 8 | logical bucket | 0 |
| 52 | 8 | page holding it | 2 |
| 60 | 4036 | | zero |

With one bucket (maximum split bucket 1, split bucket 0) every key lands in
bucket 0 whatever its hash, so every record of both members is on page 2.

**The key hash.** A u32 computed over the key's bytes: start with
h = 5381; for each byte b in order, h = (h times 33 plus b) modulo 2^32. It
is written big-endian. This is UnQLite's default hash function. VERIFIED: it
gives the constant at offset 4 from `chm@symisc`, `0x0B8822AB` from `TOC`,
and the stored hash of every one of the 25 GUID-keyed records in the five
parts. The generator computes it for each GUID key (`exch.hash.*`); the
listing writes the hash of `TOC` and of `chm@symisc` as constants.

## 15.3.4 Page 2: the bucket page, its cells and its free block

The page begins with a 12-byte header:

| Offset | Size | Field |
|---|---|---|
| 0 | 2 | offset of the first cell in the chain (0 when the page is empty) |
| 2 | 2 | offset of the first free block |
| 4 | 8 | slave page (a continuation of this bucket): 0, none |

Each record is a cell: a 26-byte header, then the key, then the value.

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | the key hash (15.3.3) |
| 4 | 4 | key length in bytes |
| 8 | 8 | value length in bytes |
| 16 | 2 | offset of the next cell in the chain, 0 at its end |
| 18 | 8 | overflow page for a value too large for the page: 0, none |
| 26 | key length | the key |
| 26 + key length | value length | the value |

The cells lie one after another from offset 12, in the order the records
were stored. The chain runs backwards: the page header names the last cell
stored, and each cell names the one stored before it; the first stored ends
the chain. After the last cell comes one free block covering the rest of the
page: a big-endian u16 offset of the next free block (0), a big-endian u16
size (4096 minus the block's offset), then zero bytes.

Every key and value in both members has a fixed length (the GUIDs are always
36 characters), so the offsets are constants:

| Member | Cell | Offset | Key, value lengths | Next |
|---|---|---|---|---|
| Exchange2 | Front Plane | `0x000C` | 36, 399 | 0 |
| Exchange2 | Top Plane | `0x01D9` | 36, 395 | `0x000C` |
| Exchange2 | Right Plane | `0x03A2` | 36, 399 | `0x01D9` |
| Exchange2 | `TOC` | `0x056F` | 3, 288 | `0x03A2` |
| Exchange2 | document | `0x06AC` | 36, 122 | `0x056F` |
| Exchange2 | free block | `0x0764` | size `0x089C` | |
| ConfigHeader | configuration header | `0x000C` | 36, 69 | 0 |
| ConfigHeader | free block | `0x008F` | size `0x0F71` | |

VERIFIED (all five parts): these are the offsets, lengths and links in both
members; nothing is stored past a free block's header.

## 15.3.5 The reference plane records

Each value is MessagePack. The conventions throughout both members
(VERIFIED, every record of the five parts):

- A map's keys are in ascending byte order (`S` sorts before `c`). Some keys
  appear twice in one map, and the pair count includes both.
- A string is a fixstr when it is 31 bytes or shorter, else a str 8
  (`0xD9`, length byte).
- A small integer is a positive or negative fixint; `true` is `0xC3`,
  `false` `0xC2`.
- A real is always a float 64 (`0xCB`, then the big-endian double), and a
  negative zero is kept as one.

Each plane record is a map of 15 pairs:

| Key | Value | Notes |
|---|---|---|
| `class` | `moRefPlane_c` | written twice |
| `description` | the plane's name | |
| `hidden` | 0, then `true` | written twice, as an integer and as a boolean |
| `id` | 2, 3, 4 for Front, Top, Right | HYPOTHESIS: the plane's id in the feature tree |
| `name` | the plane's name | |
| `normal` | array of 3 reals | Front (0, 0, 1), Top (0, 1, 0), Right (1, 0, 0) |
| `point` | array of 3 reals | (0, 0, 0) |
| `subtype` | `swRefPlaneSWStandard` | |
| `suppressed` | 0, then `false` | written twice |
| `transform` | map of 2: `class` `mgXform_c`, `elems` an array of 13 reals | below |
| `updatestamp` | 101 | written twice; HYPOTHESIS: an update counter. The same in all five parts, whatever their features |

The 13 `elems` are a 3 by 3 matrix by rows, a translation of three, and a
scale. Front: rows (1, 0, 0), (0, 1, 0), (0, 0, 1). Top: (1, 0, 0),
(0, 0, -1), (0, 1, 0). Right: (-0, -0, -1), (0, 1, 0), (1, 0, 0), the first
two written as negative zero. Translation (0, 0, 0), scale 1. The third row
equals the plane's normal (VERIFIED); that the rows are the plane's axes in
model space and the last four values a translation and a scale is
HYPOTHESIS.

## 15.3.6 The table of contents

Key `TOC`, a map of 2 pairs: `class` `object-map`, and `model`, a map of 4
pairs: `class` `moPart_c`, `configid` 0, `configname` `Default`, and
`object`, a map of 4 pairs: `class` `moRefPlane_c`, then three pairs each
keyed `object` whose value is a map of 2 pairs: `class` `object` and `guid`,
a plane record's GUID as a str 8 of 36.

The order of the three plane GUIDs is the free slot `exch.toc`. SOLIDWORKS
wrote them as Front, Top, Right in o02, o03 and o07, and in two other orders
in o01 and o12. No ordering of the GUIDs explains it (tried: as text, as
bytes in either order, by the key hash, by FNV-1a and CRC-32, each modulo
small powers of two), so it is most likely the order of objects in memory.
The generator writes Front, Top, Right, an order SOLIDWORKS itself writes;
that a reader treats the list as a set is HYPOTHESIS.

## 15.3.7 The document record

A map of 5 pairs: `SaveAsNewCalled` `false`, `class` `uiPartDoc_c`,
`platformflag` 2, `repairDTForDefaultConfigflag` `false`,
`useEnglishDescriptionForWeldmentCutList` `false` (a key of 39 bytes, so a
str 8). The values are the same in all five parts; what each flag governs is
UNKNOWN beyond its name.

## 15.3.8 The configuration header record

The only record of `3DExperienceExchange_ConfigHeader`: a map of 4 pairs,
`class` `dmConfigHeader_c`, `configHeaderfamilyMemberID` -2 (negative
fixint `0xFE`), `id` 0, `name` `Default`.

The configuration name `Default` appears here and in the table of contents.
The listings are proved only with that name, which is the name of the
template's one configuration. A generator that named the configuration
otherwise would change these strings, the value lengths and the cell offsets
of 15.3.4 by the rules above; that is not proved and not specified.

## 15.3.9 A smaller database: an untested alternative

HYPOTHESIS, not tested against SOLIDWORKS: the records only repeat what the
part's other streams hold (the standard planes, the configuration's name,
document flags at their defaults), and SOLIDWORKS rewrites at least the
configuration header on every save (15.3.1). It may therefore accept an
empty database in either member (page 0 and page 1 as above, page 2 with
first cell 0 and one free block from offset 12 of size `0x0FF4`), or no
such members at all, and rebuild them. The specification writes what the
fixtures hold, because only that is proved. A trial of the empty form on a
SOLIDWORKS installation would settle it.

## 15.3.10 Open questions

  writes them for the 3DEXPERIENCE platform (UNKNOWN).
- What `updatestamp`, `platformflag`, `configHeaderfamilyMemberID` and the
  document flags mean (UNKNOWN), and whether `id` is the feature tree id
  (HYPOTHESIS).
- Whether a part with more than one configuration, or with features other
  than sketches and extrusions, adds records here (UNKNOWN: no fixture in
  scope has either).

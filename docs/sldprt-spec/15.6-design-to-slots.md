# 15.6 From a design to the slots

This section says how `plan` (15.0.7) turns a `ParametricDocumentIR` part
(`docs/NATIVE_SLDPRT_WRITER.md` section 8, `ir.py`) and an `Identity` into the one slot
dict every listing reads: what it supports, what it refuses, the rule for every design
and derived slot, and the value the generator writes for every identity and free slot.
Every slot any listing reads is in a table of this section or in README 15.0.2. Units
are the IR's: metres. All arithmetic is IEEE 754 double precision, in the order the
rule writes it: `a + b + c` is `(a + b) + c`, and `x²` is `x * x`.

VERIFIED (`tests/test_sldprt_spec.py`, analysis side): an implementation of these rules
on the analysis side, given o01, o02, o03, o04, o07 and o12 written as IR designs (o04 is
o02 with three file custom properties) and only their identity and free values read from
each part, assembles all 35 members of each part byte for byte. A box with a hole has no
such fixture; its records are proved on o10 and o11 as 15.5.10 says, and the members a cut
changes as 15.1.6, 15.2 and 15.4.6 say.

## 15.6.1 The steps of `plan`

1. Run `ir.validate(doc)`; an `IRError` passes through unchanged.
2. Accept or refuse each item of the timeline (15.6.2). Refused items raise
   `NativeWriteUnsupported`, or with `allow_partial` are left out (15.6.7).
3. Accept or refuse each file custom property (15.6.9), in the same way as the timeline's
   items.
4. Build `features` (15.6.2), `bodies` (15.6.4), and the model, plane and header slots
   (15.6.3).
5. Take the identity values from `identity`, or make them (`Identity`, 15.6.6), and fill
   every identity and free slot by 15.6.6.
6. Build `props` and `props_by_name` (15.6.9), and compute the slots derived from
   identity values (15.6.5).

`assemble(slots)` then assembles each listing of the member table (15.0.1) with the
whole dict. `Contents/Config-0-ResolvedFeatures` continues the archive
`Contents/Config-0` leaves (15.0.4): assemble `config-0.srl` first and go on with its
archive.

## 15.6.2 What the generator supports, and the `features` list

The generator writes one or more corner rectangles on the Front Plane, each extruded
blind towards +Z, the first as the part's first body and every later one as a new
body (merge off). After a single such box it may write one round hole: a circle on the
Front Plane cut through all in both directions. It also writes a part with no features
at all (o01's form). The IR's timeline is read in order and must be a sequence of pairs:
a sketch, then at once the one extrusion that uses it. A sketch whose curves are all
circles, at least one, is checked as the hole's (below), so a sketch of several circles
is refused there; every other sketch, one that mixes a circle with lines included, is
checked as a rectangle's and refused as "sketch is not a single corner rectangle".

**A sketch is accepted** when all of these hold; otherwise the item is refused with
the reason in brackets:

| Condition | Refused as |
|---|---|
| `plane` is the base plane `xy` (origin (0, 0, 0), x (1, 0, 0), y (0, 1, 0)): SOLIDWORKS' Front Plane | "sketch on a plane other than the Front Plane" |
| not `suppressed` | "suppressed sketch" |
| its curves are exactly four lines, none construction | "sketch is not a single corner rectangle" |
| the lines join four distinct corners in one closed loop, each corner the end of two lines (the point id `origin` stands for (0, 0)) | the same |
| two lines are parallel to x and two to y (end points equal in y, or in x, exactly) | "rectangle is not aligned with the sketch axes" |
| width and height are positive | "degenerate rectangle" |
| it is used by exactly one extrusion, the next item of the timeline | "sketch not followed by its extrusion" |

**An extrusion is accepted** when:

| Condition | Refused as |
|---|---|
| `sketch` is the item just before it | "extrusion does not follow its sketch" |
| `end` is `blind` and `direction` is `forward` | "only blind extrusions towards the sketch normal are written" |
| `depth` is positive and finite | (the IR's validation already requires it) |
| `profile` is `None`, or one loop of exactly the rectangle's four lines | "profile is not the whole rectangle" |
| the first extrusion: `operation` is `new_body` or `join` (both make the first body) | "the first extrusion cannot cut" |
| a later extrusion: `operation` is `new_body` | "a later extrusion that joins or cuts is not written yet (only merge off is proved)" |
| not `suppressed` | "suppressed extrusion" |

**A circle sketch is accepted** when all of these hold:

| Condition | Refused as |
|---|---|
| `plane` is the base plane `xy`, as a rectangle's | "sketch on a plane other than the Front Plane" |
| not `suppressed` | "suppressed sketch" |
| its curves are exactly one circle (`kind` `circle`, its centre point and `radius`), not construction; a sketch of several circles is refused | "a sketch with more than one circle is not written yet" |
| the radius is positive | "degenerate circle" (not reachable today: step 1 of 15.6.1 runs `ir.validate`, which already rejects a circle whose radius is not a positive finite number with an `IRError`; the row stays so the check holds if validation ever allows it) |
| it is used by exactly one cut, the next item of the timeline | "sketch not followed by its extrusion" |

**Its cut is accepted** when:

| Condition | Refused as |
|---|---|
| `sketch` is the item just before it | "extrusion does not follow its sketch" |
| `operation` is `cut` | "a circle is written only as the profile of a cut" |
| `end` is `through_all` and `direction` is `midplane`: through all in both directions (`depth` is not read) | "only a cut through all in both directions is written" (a cut through all one way, or blind, has end conditions no fixture shows: 15.5.13) |
| the part has exactly one box before it, and the cut is the last item of the timeline | "a cut is written only as the last feature of a part with one box" |
| the circle lies inside the box's rectangle: `x0 < cx - r`, `cx + r < x1`, `y0 < cy - r` and `cy + r < y1` | "the circle is not inside the box's rectangle" |
| `profile` is `None`, or one loop of exactly the circle | "profile is not the whole circle" |
| not `suppressed` | "suppressed extrusion" |

Why these: the cut's records name the one body they cut by its faces and make one new body
from it, and they name the faces the hole runs between, the box's two caps (15.5.13).
With a second body, a circle that crosses the box's outline, a second cut or a feature
after the cut, the bodies and faces SOLIDWORKS would name are not the ones the fixtures
show. A circle that runs outside the box would cut nothing there, or cut its side faces,
whose records no fixture holds.

**Every other feature is refused**, one item each: `Revolve` ("revolves are not
written yet"), `Fillet`, `Chamfer`, `Hole`, `Pattern`, `Mirror` (the same, by kind),
and `Unsupported` (its own `reason`). A design with any refused item raises
`NativeWriteUnsupported` listing all of them, unless `allow_partial`; with it, the
refused items are left out (and named in `left_out`), together with every item that
depends on one (an extrusion of a refused sketch, a feature after a refused one that
uses its result).

**The items.** For the k-th accepted pair (k from 0), sort the rectangle's corners so
that `x0 = min x`, `y0 = min y`, `x1 = max x`, `y1 = max y` (sketch coordinates; on the
Front Plane, model x and y). `features` is the list of the items, sketch then
extrusion, pair by pair. Every field, its kind and its rule (identity and free fields
take the value the generator writes; the tests pass a fixture's values instead):

| Field | Item | Kind | Type | Rule, or the value the generator writes |
|---|---|---|---|---|
| `name` | both | design | text | `"Sketch<k+1>"`, `"Boss-Extrude<k+1>"`, whatever the IR calls them; a hole's cut is `"Cut-Extrude1"` |
| `sketch` | both | design | bool | true for the sketch, false for the extrusion |
| `circle` | sketch | design | bool | false for a rectangle, true for a hole's circle |
| `cut` | extrusion | design | bool | false for a boss, true for a hole's cut |
| `log_modified` | both | derived | bool | true for a rectangle's sketch, false for a circle's and for every extrusion (15.2.2.2) |
| `id` | both | derived | u32 | the creation number: a counter starting at 26; a sketch takes the counter and adds 6 to it when it is the part's first sketch, 7 when it is a later one; an extrusion or a cut takes the counter and adds 1 (15.5.4) |
| `corners` | both | design | 4 f64 | `[x0, y0, x1, y1]`; the extrusion's is its sketch's (not on the hole's items) |
| `at_origin` | sketch | derived | bool | `x0 == 0.0 and y0 == 0.0`; false for a circle |
| `sketch_name`, `sketch_id` | extrusion | derived | text, u32 | its sketch's `name` and `id` |
| `depth` | extrusion | design | f64 | the IR's `depth` |
| `depth_text` | extrusion | derived | text | `depth * 1000`, rounded to 8 decimal places, written with 8 decimals, then trailing zeros and a trailing point removed (`30`, `31`, `10`; 15.1.2.2) |
| `first` | extrusion | derived | bool | `k == 0` |
| `merge` | extrusion | derived | bool | `k == 0` |
| `centre` | extrusion | derived | 3 f64 | `[(x0 + x1) / 2, (y0 + y1) / 2, depth / 2]` |
| `diagonal` | extrusion | derived | f64 | `sqrt((x1 - x0)² + (y1 - y0)² + depth²)` |
| `body_id` | extrusion | derived | u32 | `101 + k` |
| `body_label` | extrusion | derived | text | `"body<k+1>"`, the label of its body's `moAtom_c` (15.4.6) |
| `created` | both | identity | u32 | `doc.created` |
| `modified` | sketch | identity | u32 | `doc.created` |
| `time` | both | identity | u64 FILETIME | `doc.filetime` |
| `cache_memo` | both | free | f64 | 0.0 |
| `regen` | sketch | free | u32 | 103 |
| `cache_text` | extrusion | free | f64 | `x1 * 0.2` |
| `counter_marks` | extrusion | free | u16 | 7 |
| `counter_favorite` | extrusion | free | u32 | 0 |
| `counter_face1`, `counter_face2` | extrusion | free | u32 | 0, 0 |

sketch coordinates) and the box's extrusion item `box` (the first extrusion):

| Field | Item | Kind | Type | Rule, or the value the generator writes |
|---|---|---|---|---|
| `centre` | circle | design | 2 f64 | `[cx, cy]` |
| `radius` | circle | design | f64 | `r` |
| `start` | circle | derived | 2 f64 | `[cx + r, cy]`, the point the circle starts at (15.5.12) |
| `regen` | circle | free | u32 | 102 |
| `sketch_name`, `sketch_id` | cut | derived | text, u32 | its circle's `name` and `id` |
| `first`, `merge` | cut | derived | bool | false, false |
| `centre`, `diagonal` | cut | derived | 3 f64, f64 | the box's `centre` and `diagonal`: the body's box, which the hole leaves as it was |
| `body_id`, `body_label` | cut | derived | u32, text | the body the cut makes: `101 + n` and `"body<n+1>"`, n the number of boxes (here 1: 102, `"body2"`) |
| `target_id`, `target_label`, `target_uid` | cut | derived | u32, text, u32 | the box's `body_id`, `body_label` and `id` |
| `target_created` | cut | derived | u32 | the box's `created` |
| `ring` | cut | derived | list of 5 | the faces of 15.5.13's ring, each `{end, uid, created, face}`: `end` true for an end face, `uid` and `created` the box's `id` and `created`, `face` the number: (false, 4), (true, 1), (false, 3), (true, 0), (false, 1) in that order |
| `created`, `time`, `cache_memo` | cut | identity, free | | as a box's |

| `counter_face1`, `counter_face2` | cut | free | u32 | 0, 0 |

Inside the feature stream's `@for f in $features`, `$f_index` is the item's position in
`features` from 0 (15.5.4, 15.5.7). Sections 15.1, 15.2 and 15.5 explain the fields they
read; the free values are justified in 15.5.9 and the identity values in 15.5.4.

`at_origin` is true exactly when the minimum corner is the origin: the IR's `origin`
point or a point whose coordinates are both 0.0. The fixtures show the tie records only
on that corner; a rectangle with another corner on the origin (one lying in negative x
or y) is written with `at_origin` false and reported (15.6.7).

**Names.** The part's features are named `SketchN`, `Boss-ExtrudeN` and `Cut-Extrude1`,
the names SOLIDWORKS gives, whatever the IR calls them; `plan.names` maps each IR feature id and
name to the part's name. VERIFIED names (every fixture); the names also key the
`objref` labels of 15.5.6, and these are unique and distinct from the other labels.

**Proved and not proved.** The listings are proved byte for byte for: no features;
one pair with `at_origin` (o02, o03, o07); and two pairs, the first with `at_origin`
and the second without (o12). The other combinations the rules above allow are
assembled from the same listings by the same rules: a first sketch off the origin, a
later sketch on it, three or more pairs, a box with a hole. Their bytes follow from the
listings, and a box with a hole's records are each proved on o10 and o11 (15.5.10) but for
the ring of 15.5.13, derived from o11's by a stated rule (HYPOTHESIS). A check
by hand in SOLIDWORKS 2024 on 2026-10-20 opened generated parts with three pairs and with
a first sketch off the origin, and the three-pair part rebuilt to an edited depth
(VERIFIED for three pairs, `docs/NATIVE_SLDPRT_WRITER.md` 6.2). The off-origin part and
a later sketch on the origin were not examined as closely, and the creation-number gap
(15.5.4) is still a HYPOTHESIS; the check of `docs/NATIVE_SLDPRT_WRITER.md` section 7
is the test for each. A second check by hand on 2026-10-21 opened two boxes with a hole,
one at the origin and one with its first sketch off it, as one body with the hole in
place (VERIFIED on open, 6.2 of that document). That SOLIDWORKS accepts the ring is not
proof that its bytes are the ones SOLIDWORKS would write: the ring stays a HYPOTHESIS.

## 15.6.3 The model box, the bounding sphere and the planes

Each box extrusion gives a box `lo = (x0, y0, 0.0)`, `hi = (x1, y1, depth)`; a hole's cut
gives none, since the hole lies inside its box and leaves the model box, the sphere and the
planes as they were (15.5.13). A part with at least one box is **solid**. All slots below
are derived.

| Slot | Type | Rule |
|---|---|---|
| `model.solid` | bool | at least one box |
| `model.min`, `model.max` | 3 f64 each | componentwise minimum of the `lo`s and maximum of the `hi`s; (0, 0, 0) twice when not solid |
| `model.centre` | 3 f64 | `(min + max) / 2` per axis |
| `model.sphere` | 4 f64 | the bounding sphere's centre (three) and radius, by the merge below; four zeros when not solid |
| `hdr.centre` | 3 f64 | the same sphere's centre as `Header2` computes it, by the merge below; three zeros when not solid |
| `model.origin_refs` | u32 | the number of sketch items with `at_origin` |
| `planes.<p>.hu`, `planes.<p>.hv` | f64 each | for `p` in `front`, `top`, `right`: half the display rectangle's sides on the plane's axes u and v (below) |
| `planes.<p>.min`, `.max`, `.centre` | 3 f64 each | the rectangle's corners and centre in model space (below) |
| `planes.<p>.radius` | f64 | half the rectangle's diagonal (below) |

**The sphere.** A box's sphere has centre `(lo + hi) / 2` per axis and radius
`sqrt((hi.x - lo.x)² + (hi.y - lo.y)² + (hi.z - lo.z)²) / 2`. Start with the first box's
sphere as `c`, `r`, and with `h = c`. For each later box, in timeline order, with sphere
`c2`, `r2`:

    d = sqrt((c2.x - c.x)² + (c2.y - c.y)² + (c2.z - c.z)²)
    if d + r2 <= r:  nothing changes
    elif d + r <= r2:  c = c2, h = c2, r = r2
    else:
        R = (d + r + r2) / 2
        h = c2 - (c2 - h) / d * (R - r2)      per axis: difference, quotient, product
        c = c + (c2 - c) * (R - r) / d        per axis: difference, product, quotient
        r = R

`model.sphere` is `c` and `r`; `hdr.centre` is `h`. The two centres differ in the last
bits; `Header2` (15.2.2.6) writes `h`, `Contents/Config-0` (15.4.5) and `LWDATA`
(15.2.5.1) write `c`; all three write the radius `r`. VERIFIED bit for bit on o02, o03,
o07 (one body) and o12 (two); the merge for three or more bodies is a HYPOTHESIS.

**The planes.** Each plane has two axes in model space: Front u = x, v = y; Top u = x,
v = z; Right u = z, v = y. When solid, with `e` the model's extent on an axis
(`max - min`), the half side is `e / 2 + e / 2 * 0.1`; `hu` is that of axis u and `hv`
that of axis v. When not solid, `hu` is 0.08899 and `hv` 0.05500000000000001 for every
plane (the template's rectangle). Then, with `m = model.centre`, `min` and `max` are
zero on the plane's normal axis, and

    min.u = m.u - hu,  max.u = m.u + hu,  min.v = m.v - hv,  max.v = m.v + hv
    centre = (min + max) / 2   per axis
    radius = sqrt((max.x - min.x)² + (max.y - min.y)² + (max.z - min.z)²) / 2

The feature stream (15.5.5) writes `hu`, `hv` and `model.centre`; `LWDATA` (15.2.5.3)
writes `centre`, `max`, `min`, `radius`, `hu` and `hv`. VERIFIED bit for bit on all
five parts (o01's is the not-solid form).

Overlapping or touching boxes are written as they are: with merge off each is its own
body, and SOLIDWORKS rebuilds the bodies from the features (o12's touch nothing; an
overlap is a HYPOTHESIS).

## 15.6.4 Bodies

One body per extrusion, a box's or a cut's, in timeline order. A cut makes its body from
the box's body, which it uses up: that body stays in the list, no longer `live`. `bodies`
is the list of the k-th body's fields, for k from 0:

| Field | Kind | Type | Rule, or the value the generator writes |
|---|---|---|---|
| `id` | derived | u32 | `101 + k` |
| `name` | derived | text | the extrusion's `name` (`SwDocContentMgrInfo`, 15.1.6) |
| `label` | derived | text | `"body<k+1>"`, the extrusion's `body_label` (15.4.6) |
| `feature` | derived | u32 | the extrusion's `id` |
| `last` | derived | u32 | the creation number of the last feature that built the body: `feature` (nothing the generator writes changes a body after it is made) |
| `changed` | derived | list of u32 | the features that changed the body after it was made: empty (o11's fillets fill it, 15.2.7.4) |
| `live` | derived | bool | false for the body a cut used up, else true |
| `from` | derived | list of u32 | the body ids it was made from: a cut's body, `[target_id]`; else empty |
| `into` | derived | list of u32 | the body ids made from it: the box's body, `[the cut's body_id]` when a cut follows; else empty |
| `regen` | free | u32 | `1151 + 2 * k` (15.4.6) |
| `time` | identity | u64 FILETIME | `doc.filetime` (15.2.7.5) |

Listings that write the bodies newest first loop `@for b in $bodies reversed`.
VERIFIED (o02: body 101 from creation number 32; o12: 101 from 32 and 102 from 40; o11:
101 from 32, used up, and 102 from its cut, 42; o10: 101 from its import, used up, and 102
from its cut). An extrusion that merges into an earlier body is not written (15.6.2), so
the case where a body would take a later feature's name does not arise; a cut's body takes
the cut's name.

**The document name.** `doc.name` is the internal title SOLIDWORKS gives a new
document in a session (`PartN`, N counting new documents), so a design does not fix it.
The generator writes `"Part1"`. The design's own name goes into `meta.file_stem`, not
here. VERIFIED form (every fixture's is `PartN`); that SOLIDWORKS does not care which N
is a HYPOTHESIS (b3 and b4 carried another document's name into a part saved
elsewhere, and opened).

**The change stamps.** `doc.stamp` and `doc.stamp2` count operations of the session
that built the part, so a design does not fix them (15.1.2.1). This is the one rule for
them:

| Extrusions n | `doc.stamp` | `doc.stamp2` | `fixed.id_base` | Fixture |
|---|---|---|---|---|
| 0 | 102 | 101 | (not read) | o01 |
| 1 | 120 | 105 | 107 | o02, o03, o07 |
| 2 | 140 | 111 | 125 | o12 |

their features, took a dimension edit and saved (VERIFIED,
`docs/NATIVE_SLDPRT_WRITER.md` 6.1).

where its own parts hold instants a second or so apart, is a HYPOTHESIS until a
generated part is checked on the PC; 15.2.1 and 15.5.9 give what the fixtures show
about times and counters taken from another document.

## 15.6.7 What is reported as left out

`plan.left_out` lists, in words for the person exporting, everything of the design that
the part does not carry. Each entry names the IR feature (its name) and says what is
missing and what the part has instead:

| The design has | The entry says |
|---|---|
| a sketch dimension (`Dimension`, driving or driven) | "<sketch>: dimension <name> (<kind>, <value in mm or degrees>) is kept as geometry only; the rectangle has no driving dimensions in the part" (for a circle: "the circle has no driving dimensions in the part"), where <name> is the name of the `Parameter` that drives it, or the dimension's id when none does; when that parameter has an expression that is not a plain number (below), the entry goes on "; its expression <text> is not kept" |
| a constraint in a circle sketch | "<sketch>: relation <kind> on <ids> is not written; the circle keeps its centre and radius" |
| points of a circle sketch other than its centre | "<sketch>: point <id> is not written" |
| a cut's `depth` | nothing: a cut through all reads no depth |
| a constraint other than the rectangle's own (`horizontal` and `vertical` on its lines, `coincident` of its corners, and `coincident` of the minimum corner with the origin) | "<sketch>: relation <kind> on <ids> is not written; the rectangle keeps its horizontal, vertical and corner relations" |
| the origin on a corner other than the minimum corner | "<sketch>: the corner on the origin is not tied to it" |
| points not used by the rectangle | "<sketch>: point <id> is not written" |
| a depth driven by a `Parameter` whose `expression` is not a plain number | "<extrusion>: depth <value> mm is written as a number; the expression <text> is not kept" |
| the first extrusion with `operation` `join` | "<extrusion>: written as a new body (there is nothing to join)" |
| any refused item, with `allow_partial` | the refusal's reason, as in 15.6.2 |
| a refused file custom property, with `allow_partial` | the refusal's reason, as in 15.6.9, followed by "; the part does not carry this property" |

An expression is a **plain number** when, with spaces removed, it is an optional sign,
digits with at most one decimal point, and at most one unit from `mm`, `cm`, `m`, `in`,
`deg` and `°`, as in `10`, `-2.5`, `40 mm` or `90deg`: the part keeps that value, so
nothing is lost and no entry is written for it. One dimension gives one entry.

The part's own relations are exactly the corner rectangle's (15.5.7), so a design that
relied on others to stay rectangular still opens as a rectangle; what it loses is the
ability to drive the rectangle by a dimension. The extrusion's depth stays editable in
SOLIDWORKS through D1 (`docs/NATIVE_SLDPRT_WRITER.md` 6.1).

## 15.6.9 File custom properties

The generator writes the design's file custom properties, `doc.properties`: the ones
SOLIDWORKS shows under File, Properties, Custom. Each is written as a plain value of its
type, unlinked, in the design's order. They go into two members, `Contents/CusProps`
(15.2.4) and `docProps/custom.xml` (15.1.4), and into no other: o04 against o02 differs
elsewhere only in identity and free values (the file name, the save times, the exchange
database's time and configuration GUID, the Biography's save record and
`config0.length_memo`), and o05, o04 with a material, has o04's bytes in both members
(VERIFIED). With no properties both lists are empty and both members are the ones the
property-less parts hold (VERIFIED, o01, o02, o03, o07, o12).

The IR holds no configuration properties, no linked values and no material, so none is
written; o14's configuration property and its linked `Mass` and `Material` are outside
what this section specifies.

**A property is accepted** when all of these hold; otherwise it is refused with the reason
in brackets, item by item like a feature (15.6.1), and with `allow_partial` left out and
named in `left_out` (15.6.7). Every rule below counts only the accepted properties.

| Condition | Refused as |
|---|---|
| its name and, for a text property, its value hold no character below U+0020 (tab and line breaks included), no lone surrogate (U+D800 to U+DFFF) and neither U+FFFE nor U+FFFF: XML cannot hold these, or would change them on reading | "property <name>: its name (or text) holds a character a part cannot store (a control character such as a line break)" |
| a text value holds no `$PRP` (in any case), and does not hold both a double quote `"` and an at sign `@` | "property <name>: SOLIDWORKS would read this text as a link to another value" |
| a whole number (an `int`) lies from -2147483648 to 2147483647 | "property <name>: the whole number <value> is outside the range a part stores" |
| a date is 1601-01-01 or later | "property <name>: a date before 1601-01-01 cannot be stored" |
| the design has at most 65,534 accepted properties | "more than 65,534 file custom properties" (one item for the design; with `allow_partial` the properties after the 65,534th are left out) |

Why these: SOLIDWORKS evaluates a value that names something in double quotes with an `@`
(`"D1@Sketch1"`, a dimension; `"SW-Mass@part.SLDPRT"`, the mass) or refers to another
property with `$PRP:`. o14's two linked properties are of the first form, stored with the
expression beside a different evaluated value (VERIFIED, `docs/FORMAT.md` 11.1); the second
is SOLIDWORKS' published syntax for referring to a property. Written as plain text, such a value
would be a link with nothing evaluated beside it, and SOLIDWORKS would show the value it
evaluates, not the design's text (HYPOTHESIS; the refusal avoids it). A number is stored
as a 32-bit `vt:i4` when whole (15.1.4). A date is stored as a FILETIME, which starts at
1601. The property list's length is written as a u16 (15.2.4). The IR already requires a
name that is not blank and unique without regard to case, a value of the property's type,
a finite number and a `YYYY-MM-DD` date (`ir.validate`). No limit on the length of a name
or a value is known (UNKNOWN), so none is applied; the CString forms of 15.0.3 hold any
length.

**The `props` list.** For the k-th accepted property (k from 0), an item with exactly
these fields:

| Field | Kind | Type | Rule |
|---|---|---|---|
| `name` | design | text | the IR property's `name`, as it is |
| `pid` | derived | u32 | `3 + k` |
| `code` | derived | u32 | the CusProps type code: text 0, date 1, number 2, yes or no 3 |
| `type_id` | derived | u32 | the XML `TypeID`: text 30, date 64, number 3, yes or no 11 |
| `vt` | derived | text | the XML value element: text `lpstr`, date `filetime`, number `i4` when the value is an `int` and `r8` when it is a `float`, yes or no `bool` |
| `text` | derived | text | the value as SOLIDWORKS keeps it typed (below) |
| `xml_text` | derived | text | `text` escaped for element text (below) |
| `xml_value` | derived | text | the stored value (below), escaped the same way |

`text` and the stored value, by type:

| Type | `text` | stored value |
|---|---|---|
| text | the value as it is | the same |
| number, `int` | decimal, with `-` for a negative value and no leading zeros: `42` | the same |
| number, `float` | Python's `repr` of the value, the shortest decimal that reads back as the same double; when that has an exponent, the same value written out without one (`format(Decimal(repr(v)), "f")`); then `.0` appended when there is no decimal point: `3.25`, `7.0`, `0.00001` | the value with six decimals, correctly rounded from the double, as C's `%f` writes it: `3.250000` |
| date | month, day and year in decimal, no leading zeros, joined by `/`: `3/15/2024` | noon on that date in the saving machine's time, written in UTC: the instant `YYYY-MM-DD 12:00:00` minus `meta.utc_offset` minutes, as `YYYY-MM-DDTHH:MM:SSZ`. The generator's `meta.utc_offset` is 0 (15.6.6), so it writes `2024-03-15T12:00:00Z` |
| yes or no | `Yes` for true, `No` for false | the same |

**Escaping.** `xml_text` and `xml_value` are written into `custom.xml` with `utf8`, not
through `${...}`, so they carry their own escaping: `&` as `&amp;` (first), `<` as `&lt;`,
`>` as `&gt;`, and `"` left as it is, which is how SOLIDWORKS writes element text (VERIFIED
for `<`, `>` and `"`: o14's FPVals hold `&lt;` and `&gt;`, and its hidden link properties a
bare `"`; `&amp;` follows XML 1.0 and is a HYPOTHESIS). The name
goes through `${p.name}` and takes the attribute escaping of 15.1.2, `"` included. `text`
itself is not escaped: CusProps stores it as a CString.

**The `props_by_name` list.** The same items, ordered by `name` compared without case: by
the name lower-cased (Python's `str.lower`), compared by code point, and by the name itself
when two lower-cased names are equal. The XML name dictionary is written in this order
(15.1.4).

**Evidence.** VERIFIED byte for byte: o04 as a whole part (two text properties and the
whole number 42), and o14's five typed properties in both members (15.1.4, 15.2.4): text,
the whole number 7, the real number 3.25 (requested from SOLIDWORKS as a Double, which it
stores as a Number with `vt:r8`), the date 2024-03-15 entered at UTC-4, which SOLIDWORKS
stored as `2024-03-15T16:00:00Z`, and yes. The rest is a HYPOTHESIS until a generated part
is checked on the PC:

- `No` for false (no fixture has a yes or no property that is false; `No` is how the
  member's own fixed flag is written);
- negative numbers, reals other than 3.25, a `float` with a whole value written as a real
  (`7.0`), and the `%f` form of very large or very small reals;
- the date at noon UTC: the fixtures' dates are at UTC-4, and the date as typed is in the
  US form that `bio.locale` 1033 names; that a SOLIDWORKS set to another locale reads it
  as the same date is not shown;
- more than three file properties in one part (o14 holds eight properties in all, numbered
  0 to 7, but only five of them are in this form);
- non-ASCII names and values (UTF-8 in the XML and UTF-16 in the CString, as `doc.name`
  and the file name are written, VERIFIED for those on o17), an empty text value, and the
  order of two names that differ where one has `_`, `[`, `\`, `]`, `^` or `` ` `` and the
  other a letter (the case-insensitive order is VERIFIED on `ISolidWorksInformation.xml`'s
  62 names, 15.1.4, but no name there tells whether the comparison lower-cases or
  upper-cases);
- that SOLIDWORKS reads the property from either member alone: which of the two it loads
  is UNKNOWN, and the generator writes both so they agree.

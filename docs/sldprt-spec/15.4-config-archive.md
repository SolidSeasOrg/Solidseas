# 15.4 `Contents/Config-0`: the document's settings archive

`Contents/Config-0` is the first half of one MFC `CArchive` (15.0.4); the feature
stream, `Contents/Config-0-ResolvedFeatures` (15.5), is the second. It holds the
part object, its internal name, the appearance, the units, the stored box of the
model, one record per body, the drafting and annotation settings, the lights, the
named views and a few managers. It is written uncompressed, not wrapped in ZLB.

| Listing | What it gives | Bytes in o01, o02, o12 |
|---|---|---|
| `config-0.srl` | the member; includes the five below | 24,240, 25,098, 25,202 |
| `config-0-macros.srl` | the feature record and the sketch records, shared with 15.5 | (definitions) |
| `visual-properties.srl` | section 15.2.9's `moVisualProperties_c`, reused here | |
| `config-0-settings.srl` | `moRelMgr_c`, the drafting and annotation settings | 17,326 in each |
| `config-0-lights.srl` | the Lights and Cameras folder and its four lights | 1,490 in each |
| `config-0-views.srl` | the ten named views and the feature colour table | 2,037 in each |

Coverage of the assembled member (`listing.coverage`), typed, hex and slot bytes:
o01 23,836, 76, 328 (98.3%, 0.3%, 1.4%); o02 24,470, 80, 548 (97.5%, 0.3%,
2.2%); o12 24,546, 80, 576 (97.4%, 0.3%, 2.3%). Slot bytes include fields given
by expressions and `objref`s.

**What "typed" means here.** The parts of this member whose meaning is decoded are
named in the listing's comments and below. The rest, most of `moRelMgr_c` and of the
views, is written as a typed reading: `CString`s, doubles that are lengths in metres,
angles in radians or simple values, 32-bit integers, `rep N 00` for runs of zero
bytes, and short `hex` runs where no type fits. The values are SOLIDWORKS' own and
VERIFIED byte for byte; where the comments do not name a field, its boundaries and
types are a reading (HYPOTHESIS), not a decoding. The generator writes them as the
listing gives them. They are the same bytes in every part of the fixtures (the 13
part fixtures of `docs/NATIVE_SLDPRT_WRITER.md` 4.9 for everything but the slots
below), so the specification lists them as constants.

## 15.4.1 Framing and the document node

The archive starts with next index 2 (`@archive start 2`): the first class,
`moPart_c`, takes index 2 and the part object 3; `moNodeName_c`, the second class,
takes 4, which is why every named node later in the archive starts with `04 80`.
VERIFIED (13 streams in 12 parts, 15.0.4).

`moPart_c` holds a u32 size, then a u32 0 and the u32 17000 (the format version,
`_MO_VERSION_17000`). The size is the number of bytes from the end of that field to
the start of a second size field inside `uoModelData_c` (15.4.6), and that second
field is the number of bytes from its own end to the end of the member. So the member
is three runs: 18 bytes, a settings run ending just before a u32 tail size, and the
tail. VERIFIED: the two sizes hold in all 12 part fixtures read (o01 to o07, o11 to
o14, o17), whose settings and tails differ in length by the material, the properties
and the document name. The listing writes each as an `@sized u32` block (README
15.0.3), `settings_size` from the first size field to the second and `tail_size`
from the second to the end, so the member assembles in one pass and neither size is
a slot.

The document node follows: class `moNodeName_c`, the part's internal name `doc.name`
(15.6.6), then u32 0, u32 0x40000000, u32 0 and a u32 of flags, 256 in the empty
part and 288 (0x20 more) once the part has a body (`=256+32*int($model.solid)`),
then an empty `CString` and a u32 0. VERIFIED (256 in o01; 288 in the 11 part fixtures with a
body, o02 to o07, o11 to o14 and o17).

`model.solid` is derived: true when the design has at least one extrusion (15.6.3).
Every place this member differs between the empty part and a part
with a body is written as `@if $model.solid`.

## 15.4.2 The feature record

Every feature of the archive, and every folder, light and manager that SOLIDWORKS
treats as one, carries the same record. `config-0-macros.srl` defines it once:

| Macro | Fields |
|---|---|
| `nodehead NAME FLAGS UID` | a `moNodeName_c` object (`04 80`) with the name, then `feathead` |
| `feathead FLAGS UID` | u32 0, u32 flags, u32 the creation number, u32 0, an empty `CString`, 6 zero bytes; the caller then writes a u16 child count and the children (objects, or `objref`s for children written before) |
| `feattail ID STAMP MEMO TIME` | 12 zero bytes, u32 the feature id, u32 0, u8 0, u32 17000 and u32 2024016 when `STAMP` is 1 (0 and 0 otherwise: the version and build the record was made in), u32 17000, f64 `MEMO`, u32 2024016 (the version and build it was saved in), then constants (an empty `CString`, i16 -1, u8 3, two i32 -1, f32 -1, u32 1, i32 -1), the time as a FILETIME written high word first, u16 2, u32 350108: 111 bytes |
| `touchedtail K TIME` | `feattail` for a template record SOLIDWORKS renumbers once the part has a feature: id `fixed.id_base + K` and stamped when `model.solid`, else id 101 and not stamped (15.5.4) |

Flags are 0x40000000 for folders and sketches, 0xC0000000 for planes, the origin and
lights, 0x40000140 for an extrusion. `MEMO` is 0 in every record of o02; SOLIDWORKS
leaves a length there in a few records of later saves (15.5.9). VERIFIED (all named
nodes of 5 parts). The meaning of the constants is not decoded.

## 15.4.3 Appearance

`moVisualProperties_c` is section 15.2.9's object, written with that section's
`visualprops` macro and `N=3`, with the appearance file `cmgr.texture`: the same
value `Contents/CMgr` carries. VERIFIED (5 parts give the bytes; in all 12 part fixtures read,
the path is the one `CMgr` carries). The generator writes what 15.2 gives for `cmgr.texture`,
`<SystemTexture>\graphics\materials\color.p2m`, the form SOLIDWORKS itself writes in
`ThirdPtyStore/VisualStates`; that SOLIDWORKS accepts it here is a HYPOTHESIS. The
fixtures carry an absolute installation path, which the generator never writes
(15.0.6).

## 15.4.4 Units

`moUnitsTable_c` (two bytes, u16 16) and one record per kind of unit: length (twice),
angle, number, density, float number, spring constant, unit system, force, stress,
gravity, linear and rotary motor, power, energy, time and frequency, each two u32,
doubles and u32s, then `moUnitComponent_c` (u32 2, 8 zero bytes). This is the
template's MMGS unit system (`docs/FORMAT.md` 11.6: the XML members say MMGS, mm,
g). No fixture changes units, so which field is the unit, which the decimal places
and which the angle tolerance is UNKNOWN; the generator writes the template's
records and the design's lengths in metres everywhere else.

One double in the first length record is free: `config0.length_memo`, 0 in o01,
o02, o07 and o12, 30.0 in o03, o04 and o13 (parts that were opened again before
they were saved). The generator writes 0.

## 15.4.5 The curvature object, the stored box, the plane counter

When the part has a body, `moUnitComponent_c` ends with a `gcCurvatureObject_c`
object (the doubles 1000.0, 31.6, 4.0, 1.2, 1.0, then a FILETIME
`config0.curvature_time`, written low word first as a u64); without one it ends with
a u16 0, a null object. VERIFIED (o01 against o02, o03, o07, o12).

`moTransRefPlaneData_c` then holds u32 1, u32 1, u32 0x00F78453, u32 0x00672305,
u32 95, u32 0 (not decoded, constant) and a u8: 0 in the empty part, 1 with a body, followed
in that case by ten doubles in metres: the bounding sphere's centre (three), the
model's far corner `model.max`, its near corner `model.min`, the sphere's radius.
This is the same record as `Header2`'s (15.2.2.6). The sphere is `model.sphere`
(15.6.3): one body gives the centre of its box and half its diagonal; with more
bodies each body's sphere is merged in body order into the smallest sphere holding
both, radius `R = (d + r1 + r2)/2` for centres `d` apart and centre
`c1 + (c2 - c1)*(R - r1)/d` (computed in that order: difference, product, quotient),
the form `LWDATA` uses too. VERIFIED bit for bit on o02, o03, o07 (one body) and o12
(two); three or more bodies are a HYPOTHESIS.

Further on (after constants that include the doubles 1000.0 and 1e-08) the record
has a u32 that is 1 with a body and 0 without, and near its end the u32 `=101+len($features)`: 101 in
o01, 103 in o02, o03 and o07, 105 in o12. VERIFIED (5 parts). It is the same value
section 15.2 derives as 101 plus the number of features. It is not that in every
fixture (o14, one sketch and one extrusion like o02, has 104; o11 and o13 have 106),
so it is a session counter; the value the expression gives is the one SOLIDWORKS
wrote for these designs.

## 15.4.6 Bodies

`uoModelData_c` holds 34 zero bytes, the u32 tail size (15.4.1), 6 zero bytes, u32
`=100+len($bodies)` (the newest body's id) and u32 the number of bodies, then one
`moAtom_c` per body of `bodies` (15.6.4), newest first (`@for b in $bodies reversed`):

| Field | Value |
|---|---|
| head | u16 0, u32 1, u32 0x40000000, i32 -1, u32 0, an empty `CString`, 12 zero bytes |
| u32 | the body id, `101 + k` for the k-th body from 0 (`$b.id`) |
| u32 | 0 |
| u32, u32 | the creation number of the extrusion that made the body, twice (`$b.feature`) |
| | 12 zero bytes, u32 1, i32 -1 |
| u32, u32, u32, u32 | the body's `regen`, 1, `regen` again, 6 |

Each `moAtom_c` is labelled (`as $b.label`, `body1`, `body2` ...): the extrusion
that made the body refers to it by its `body_label` (15.5.8). After the bodies the object ends with 44
bytes when the part has a body and with u32 17000, u32 10000 and four bytes
`00 00 00 10` when it has none. VERIFIED (o01, o02, o03, o07, o12; o12 lists body
102 (Boss-Extrude2, creation number 40) before body 101 (Boss-Extrude1, 32)).

A body's `regen` is free: 1151 in o02 and o03, 3412 in o07, 10997 and 11473 in o12. It
changes with every rebuild in the session. The generator writes 1151 for the first
body and 1151 plus 2 for each later one; SOLIDWORKS took o02's value in a part whose
other members came from another document (b3, b4). VERIFIED for one body, a
HYPOTHESIS for more.

The `bodies` list is defined in 15.6.4.

## 15.4.7 Drafting and annotation settings

`moRelMgr_c`, 17,326 bytes: the relation manager and the document's drafting
defaults. `swnative.typedump` reads in it the fonts (Century Gothic, sizes such as
3.5 mm as metres, Segoe UI), line styles (`CONTINUOUS`), arrow sizes and angles,
the bill of materials columns (`%Description%, %MATERIAL%` ...), the crosshatch
name and eight further length-unit records (`moLengthUserUnits_c` objects; the class
is the one 15.4.4 defined, so these are class references). The same bytes in every
part fixture (4.9). Not decoded: the listing is a typed reading (see the top of this
section), and changing these settings is outside what the generator does.

## 15.4.8 Lights and views

The `moEnvFolder_c` folder "Lights and Cameras" (creation number 6) with four
children written in place: `moAmbientLight_c` "Ambient" (12) and three
`moDirectionLight_c` "Directional1" to "Directional3" (13, 14, 15). Each light is a
full feature record with the template's id 101, not stamped, and the template's time
(the FILETIME 0x01DA7F0BEAAE8D3C), then its colour, intensities and direction as
doubles, all constant. The folder's own tail is `touchedtail` with K = 8 and the
time `fixed.lights.time`: id `fixed.id_base + 8` once the part has a feature (15.5.4).
VERIFIED (5 parts).

Then `suObList` and the ten named views as `moView_c` objects, each a name
(`*Normal To`, `*Front`, `*Back`, `*Left`, `*Right`, `*Top`, `*Bottom`, `*Isometric`,
`*Trimetric`, `*Dimetric`) and its orientation as doubles, and `moFeatColorTab_c`.
Constant. VERIFIED.

## 15.4.9 The managers

| Object | Content |
|---|---|
| `moSketchBlockMgr_c` | u16 0, `feathead` (flags 0x40000000, creation number 0xFFFFFFFF), no children, `feattail` (id 101, not stamped, time `config0.sketch_blocks_time`), u32 1, a 16-byte GUID (constant), u32 0, u16 0, then an `objref` to itself, then zero bytes. The object is labelled `sketch_blocks`. VERIFIED: the self-reference is 94 in o01, 98 in o02, 99 in o12, each the object's own index |
| `suObList` | the annotation views: u16 1 and one `moAnnotationView_c`, `*Top`, with its orientation, when the part has a body; u16 0 otherwise. Then u32 `=199+int($model.solid)` (the next annotation view's number), u32 199, u32 1, u32 199, 30 zero bytes |
| marks | when the part has a body, a `moPMarkRecord_c` object holding u32 3; without one, u16 0 (no object). Then u32 1, 12 zero bytes, u32 20, u32 0, u32 20, 16 zero bytes and a second `suObList` (u16 0, constants, two empty `CString`s) |
| `moCThreadRefMgr_c` | 23 zero bytes, then the mass properties (15.4.11) or u32 0, 0, 0 |

VERIFIED (o01 against o02, o03, o07, o12). The annotation view appears with the
first dimension (the extrusion's D1); that a part with a feature but no dimension

generator writes has D1.

## 15.4.10 Slots

Shared slots (README 15.0.2) used here: `doc.name`, `doc.stamp2`, `model.solid`,
`model.min`, `model.max`, `model.sphere`, `features` (its length), `bodies` (`id`,
`label`, `feature`, `regen`), `fixed.id_base` and `fixed.lights.time`. The section's
own slots, with the rule or the generator's value in 15.6.6:

| Slot | Kind | Type | Rule, or the fixtures' values | Generator writes |
|---|---|---|---|---|
| `cmgr.texture` | free | text | 15.2.7.3 | `<SystemTexture>\graphics\materials\color.p2m` |
| `config0.length_memo` | free | f64 | 0, or 30.0 after a reopen | 0.0 |
| `config0.curvature_time` | identity | u64 FILETIME | a time in the session | `doc.filetime` |
| `config0.sketch_blocks_time` | identity | u64 FILETIME | a session time | `doc.filetime` |
| `config0.mass_block` | free | bool | 15.4.11 | false |
| `config0.mass` | free (cache) | 12 f64 | 15.4.11 | twelve 0.0, not written while `mass_block` is false |

`fixed.lights.time` is the identity time of 15.4.8 (the template's time in o01, a
session time otherwise); the generator writes `doc.filetime`. A body's `regen` is
free, 15.4.6.

The times are VERIFIED harmless to vary only in the sense of 15.2.1: b3 and b4
carried o02's `Config-0` into o01, so SOLIDWORKS took times and counters from
another document. That it takes `doc.filetime` in all of them is a HYPOTHESIS until
a generated part is checked.

## 15.4.11 Caches

**Mass properties.** When `config0.mass_block` is true, `moCThreadRefMgr_c` holds
u32 1, u32 1, u32 the number of bodies, then per body (oldest first) u32 the body id
and u32 its mass tag and f64 1.0, then twelve doubles `config0.mass`: the centre of
mass (three), the volume, the area, the mass (equal to the volume: density 1), the
moments of inertia about the centre of mass Ixx, Iyy, Izz, and the products Ixy,
Ixz, Iyz, then constants. The last body's mass tag is `doc.stamp2` and each earlier
one 2 less (`=$doc.stamp2-2*(len($bodies)-1-$b_index)`): 105 in o02, 109
and 111 in o12. VERIFIED (o02, o03, o07, o12). The values are the bodies' exact
properties up to rounding (o02: volume 6.0e-6 m³, area 0.0022 m², Ixx 6.5e-10),
but the products of inertia carry integration noise (6.6e-27 in o02) and the last
bits cannot be derived, so the cases read them from the fixture.

The generator writes the empty form, u32 0, 0, 0: o17, the same box as o02 saved
under another name, has a body and that empty form (its doc.stamp2 is 105 as in
o02). VERIFIED that SOLIDWORKS writes it for a part with a body; mass properties are
caches SOLIDWORKS left stale and accepted in a1 to b4 (`docs/NATIVE_SLDPRT_WRITER.md`
6.1).

**The stored box and sphere** (15.4.5) are caches too, but the rule is exact, so
the generator computes them.

**Density.** `moDensityParameter_c` is a parameter like 15.5.8's D1: u16 0, u32 0,
u32 0x40000000, i32 -1, u32 0, an empty `CString`, u16 0, then the density as f64,
1000.0 kg/m³ with no material (2700.0 in o05, which has 1060 Alloy). VERIFIED
meaning (o02 against o05).

## 15.4.12 What it is proved on

`config-0.srl` gives `Contents/Config-0` byte for byte in o01, o02, o03, o04, o07
and o12 (`tests/test_sldprt_spec.py`, each case assembled with the part's one slot
dict). VERIFIED. o04 (o02 with custom properties added) differs from o02 only in
`config0.length_memo`: the archive holds nothing of the properties. Evidence of
meaning from parts outside the cases: o05 and o06 (a material) change the
appearance, the crosshatch and the density; o14 adds properties and a material;
o17 changes the name and drops the mass block; o13 (two configurations) has its
own `Config-0` per configuration and is not claimed.
